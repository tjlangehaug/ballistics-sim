1. Executive summary

The single most consequential finding in this review is that your requirements do not describe one program — they describe three, with different clocks. A validated 6-DOF trajectory solver, a fragmentation-capable continuum solver, and an interactive 3D renderer have incompatible numerical and latency needs. Every project of this kind that fails, fails by trying to run them in one loop at one time step. The architecture recommended here separates them deliberately.

The second finding is narrower but equally hard: portable GPU compute across macOS means single precision, full stop. WebGPU/WGSL has no 64-bit float type, and Apple's Metal Shading Language has never exposed double. Vulkan's shaderFloat64 is an optional feature that MoltenVK cannot fulfil on Apple silicon because the underlying API lacks the type. Any part of your simulation that needs f64 — and a trajectory integrated to match published firing tables does — must run on the CPU. The GPU's role in this application is terminal effects, particles, and rendering, not the trajectory.

The third finding concerns your build requirement. "One machine builds all three targets" is achievable for pure Rust and painful-to-infeasible for a C++ project with native graphics dependencies. Cross-compiling to macOS from anywhere requires Apple's SDK, whose licence restricts use to Apple hardware, and cross-compiled macOS binaries cannot be code-signed or notarised off-Mac. This is a legal and toolchain wall, not a skill gap. The report recommends treating per-OS CI as the real answer and local cross-compilation as a fast-iteration convenience.

2. The graphics abstraction layer

Three desktop platforms mean three native APIs: Direct3D 12 on Windows, Metal on macOS, Vulkan on Linux. The decision is which abstraction you write against.

2.1 wgpu — the recommended default

wgpu is a cross-platform, safe, pure-Rust graphics API that runs natively on Vulkan, Metal, D3D12, and OpenGL, and on WebGL2/WebGPU under WebAssembly. It is dual-licensed MIT / Apache-2.0, and serves as the WebGPU implementation inside Firefox, Servo, and Deno — meaning it is exercised by browser-grade conformance testing rather than by one studio's shipping title. The current release is 30.0.1, with a minimum supported Rust version of 1.87.

Four properties matter specifically for this project:

  • Native Metal on macOS. The metal backend is enabled by default. You do not ship MoltenVK, do not inherit its feature gaps, and do not debug a translation layer. This is the single largest practical advantage over writing Vulkan and porting.
  • Shader language flexibility. wgpu consumes WGSL (default), SPIR-V, and GLSL, translating to whatever the backend requires via its Naga compiler. You are not locked into WGSL; existing GLSL compute kernels can be brought across.
  • Compute is first-class. Compute pipelines, storage buffers, and timestamp queries are core API, not an extension. Ray tracing and mesh shading exist as explicitly experimental extension specifications — usable, but flagged as subject to change and capable of undefined behaviour if misused.
  • HDR and wide-gamut output is handled through a documented surface colour-space API covering scRGB, Display P3, and HDR10/PQ, with the honest caveat that wgpu does not tone-map for you outside *Srgb formats.

The costs are real. wgpu deliberately hides knobs that raw Vulkan and Metal expose; deep GPU profiling and debugging tooling for WebGPU remains years behind Nsight and the CUDA ecosystem; and the API tracks the WebGPU standard, which means the lowest-common-denominator feature set of a browser API constrains what is guaranteed available. Version churn is also non-trivial — Bevy moved through wgpu 25 and 26 within a single development cycle.

2.2 Vulkan plus MoltenVK — the alternative, and its tax

Vulkan is a genuinely cross-platform open standard for 3D graphics and parallel compute, Apache-2.0 / MIT licensed, with unified management of compute kernels and graphics shaders — eliminating the need for a separate compute API alongside a graphics API. Vulkan 1.4 was released in December 2024; the specification continues to advance through 1.4.3xx point releases through 2026.

But macOS support is explicitly a portability workaround. Apple devices provide no native Vulkan; support comes via MoltenVK, which implements Vulkan atop Metal and is documented as having limitations with regard to certain advanced API features. Valve arranged for MoltenVK to be open-sourced under Apache 2.0, and it is a genuinely good piece of engineering — but for a solo developer it is one more layer between your bug and its cause, and one more thing to ship and version.

Choose Vulkan directly only if you need a specific extension wgpu does not expose — cooperative matrix operations for a custom solver, or fine-grained memory aliasing for a very large particle simulation — and are willing to accept macOS as the second-class target.

3. Engine and framework layer

You need a scene graph, a camera, a PBR renderer, asset loading, UI, and input — but you need them to get out of the way of a custom solver that owns the truth about where the projectile is. That requirement disqualifies more engines than the rendering bar does.

3.1 Bevy — recommended

Bevy is a data-driven, ECS-based Rust engine, free and open source under MIT/Apache-2.0, built directly on wgpu. Its recent trajectory is directly relevant:

  • 0.16 (April 2025) moved substantially more rendering work onto the GPU — GPU-driven rendering — plus occlusion culling, decals, physically-based atmospheric scattering, and no_std target support.
  • 0.17 (September 2025) added experimental ray-traced lighting (bevy_solari, explicitly not production-ready), DLSS on RTX hardware, a headless UI widget library, a frame-time graph widget, and initial Rust hot-patching via Dioxus subsecond.
  • 0.18 continued with atmospheric occlusion, PBR shading improvements, and Solari refinements.

The published performance figures are worth quoting because they calibrate what "enough" looks like. On an RTX 4070, a scene rendered in roughly 3.5 ms — about 3.1 ms geometry, 0.4 ms material evaluation. Pushing the instance count past one million raised the total only to about 4.5 ms: a 30% increase in GPU time for an almost 8× increase in scene complexity. The same team measured a comparable small scene at 2.2 ms in 0.16 versus 1.3 ms in 0.17. For a ballistics application — a range, a handful of targets, a debris field — rendering will not be your bottleneck.

Honest caveat on Bevy. Bevy is pre-1.0 and breaks API every release. The 0.17 event/observer overhaul renamed buffered Event to Message and forced every ecosystem crate to adapt — Avian 0.4 exists specifically to track it. For a multi-year solo project, budget real time per upgrade, or pin a version and accept that you will be behind. This is the main argument for Godot over Bevy.

3.2 Godot — the stability-first alternative

Godot is MIT-licensed with zero royalties forever, has a Vulkan-based renderer and a node-based scene system, and ships a roughly 50 MB editor. It has transitioned from hobbyist tool to professional-grade engine and is described as the primary safe harbour for developers seeking royalty-free autonomy. Two 2026 releases matter here: 4.6 (26 January 2026) made Jolt the default physics engine, closing much of Godot's prior 3D-physics gap against Unity and Unreal; and 4.7 (June 2026) added HDR output across Windows, macOS, and Linux, plus an AreaLight3D node and drawable textures. The most recent patch noted is 4.7.1 on 14 July 2026.

For your project the relevant trade is: Godot gives you a stable editor, a real asset workflow, and the same Jolt engine you would otherwise integrate by hand — but your solver becomes a GDExtension in C++ or Rust, and you are working across an engine boundary rather than inside a library. Independent assessments still place Godot behind Unity and Unreal for commercial 3D titles at significant visual fidelity, though noting the gap is minimal for medium-scale projects. At your stated bar — modern PBR, functional polish — Godot clears it.

3.3 Unreal and Unity — why they are the wrong shape here

Unreal 5.7 remains the reference for photorealistic AAA output — Nanite, Lumen, and World Partition have no Godot equivalents — and 5.7 specifically invested in tooling for small teams. Unity 6.x remains the most mature cross-platform toolchain, with Pro at $2,310/year per seat as of January 2026 following a 5% increase, and the 2023 runtime fee permanently cancelled in September 2024. Unity still powers roughly 48% of mobile game development.

Neither fits. Both are enormous — one assessment notes Unreal projects reaching 200 GB — both impose a C++/C# ecosystem you did not choose, both make deterministic fixed-step simulation harder than a library would, and neither brings anything to the specific problem of a validated 6-DOF solver. Unreal's Chaos physics is, by one account, the frustration that motivated a competing engine's creation. If you already knew Unreal deeply the calculus would differ; as a solo developer building a numerical tool with a 3D front end, the engine would own you rather than serve you.

4. Rigid-body physics engines

A critical framing point before the comparison: a game rigid-body engine is the wrong tool for the projectile, and the right tool for everything the projectile hits. Jolt's own documentation is explicit that it tries to simulate rigid-body behaviour in the real world but makes approximations, and should mainly be used for games or VR simulations. That is the correct posture. Use it for target stands falling over, debris tumbling, doors swinging, and vehicle dynamics; do not ask it to integrate a spin-stabilised projectile against tabulated aerodynamic coefficients.

4.1 Jolt Physics — recommended

Jolt is a multi-core-friendly rigid-body physics and collision-detection library, MIT-licensed, written by Jorrit Rouwe and used in Horizon Forbidden West. It is now described as the current leader in open-source 3D physics, mature and deterministic, with solid adoption as developers moved away from NVIDIA PhysX — and Godot 4.6 adopted it as its default engine.

Its engineering properties are unusually well suited to your constraints:

  • Trivial to build everywhere. C++17, depends only on the standard template library, makes no use of compiler-generated RTTI or exceptions, tested with MSVC 2019–2022, Clang 10+, and GCC 9+. Supported platforms include Windows x64, Linux x64/ARM64, and macOS x64/ARM64. Minimum x86 requirement is SSE2, with optional SSE4.1/4.2/AVX/AVX2 builds; ARM64 requires NEON with FP16. A dependency-free, exception-free, STL-only C++17 library is about as cross-compilation-friendly as native code gets.
  • Determinism is a design goal. The simulation runs deterministically, such that a simulation can be replicated to a remote client by replicating only the inputs — with documented limits. This directly serves your reproducibility requirement.
  • Concurrency model built for a custom main loop. Jolt places heavy emphasis on concurrently accessing physics data outside the main simulation update: bodies can be prepared on a background thread without locking and inserted all at once; collision queries can run in parallel with insertion and removal, and even in parallel with the simulation step by doing the broad-phase query beforehand. For an application where your own solver and a renderer both want to query the world, this is the right architecture.
  • Feature coverage relevant to you: continuous collision detection, convex hulls, compound shapes, triangle meshes, height-field terrain, a 6-DOF constraint, motors, sensors/trigger volumes, ragdolls, wheeled and tracked vehicle simulation, and water buoyancy.

Two limitations deserve honest reporting. First, the Samples application, TestFramework, and JoltViewer are Windows-only — the library is fully cross-platform but its visual debugging tooling is not, which matters for a developer working on macOS or Linux. Second, there is a documented dispute over scaling with very large static-collider counts: one user reported Jolt becoming unusable past roughly 10,000–20,000 static colliders with 200 ms+ tick times, while PhysX and bepuphysics2 handled millions under 5 ms. Rouwe responded that Horizon easily had 100,000 static colliders active with update times of a couple of milliseconds, and suggested a misconfigured object-layer setup mixing dynamic and static objects in the same broad-phase tree. A separate earlier limitation — poor scaling when all objects are in a single pile, running the whole simulation on one CPU — Rouwe has marked as fixed. Our reading: the reported failure is most likely configuration, but it is a real trap, and broad-phase layer configuration deserves explicit attention early in your integration.

4.2 The alternatives

PhysX 5 (SDK 5.5.0, BSD-3-licensed, C++, supporting Windows, macOS, and Linux among others) is a much bigger project with more features than Jolt, and demonstrably better large-static-world scaling in at least one third-party test. Rouwe's own comparison notes that in cross-engine benchmarks the "winner" depends on where you take your performance samples. PhysX is a legitimate choice, particularly given BSD-3 licensing; its disadvantage for you is bulk and an NVIDIA-centric ecosystem gravity.

Rapier (Dimforge) is the most mature pure-Rust offering, superseding nphysics, fully cross-platform with web support, and — critically for you — available in both f32 and f64 variants (rapier3d and rapier3d_f64). It is designed from the ground up for correctness, performance, and determinism, with full CCD and all standard joint types, and is reported deterministic across platforms. Dimforge also maintains Salva for 2D/3D fluid simulation, which couples with Rapier — relevant if you later model, say, ballistic gelatin or liquid-filled targets. The f64 variant is a genuinely differentiating capability no C++ game engine offers off the shelf.

Avian is an ECS-driven 2D/3D physics engine purpose-built for Bevy, successor to Bevy XPBD, with a stated design principle of utilising the ECS as much as possible. Version 0.4 tracks Bevy 0.17 and improved its contact API to expose world-space points and normal speeds. If you choose Bevy, Avian is the lowest-friction option — your solver and the physics engine share the same component storage with no marshalling.

One further candidate appeared in mid-2026 and should be flagged with explicit uncertainty. Reporting from a single secondary source describes Box3D, an MIT-licensed 3D engine from Erin Catto (author of Box2D) announced 30 June 2026, written in C17, at roughly a 916 KB release binary, with cross-platform and cross-thread-count determinism as its headline differentiator, already adopted by Facepunch Studios. The same source is clear that it is alpha, that v0.1 is not tagged, and that the API is subject to change. We could not corroborate this against a primary source within this review. If determinism across thread counts is a hard requirement for you, it is worth independently verifying — but do not plan on it.

5. External ballistics — the validated core

This is where your project's value lives, and where you will write the most original code. There is no library that will hand you a validated 6-DOF solver. What exists is a well-documented ladder of fidelity, a set of standard drag models, and published reference solutions to validate against.

5.1 The fidelity ladder

Established practice recognises a graded family of trajectory models, and mature solvers offer a user-selectable fidelity level across point-mass, modified point-mass, and 6-DOF. Patent literature in the ballistics-calculator space consistently enumerates the same canon: McCoy's McDrag algorithm, modified point-mass models, the drag models developed by the US Army Ballistics Research Laboratory, and 6-DOF models.

TIER 1
Point-mass + G-model. 3 DOF. Drag from a tabulated reference curve scaled by ballistic coefficient. Cheap, and the model the shooting world's published data speaks. Implement first — it is your validation harness.
TIER 2
Modified point-mass (MPMM). Adds yaw-of-repose, spin drift, and Magnus effects as corrections without carrying full angular state. The workhorse of artillery fire control; NATO-standardised.
TIER 3
Full 6-DOF. Tracks the bullet as a rigid body — three translation axes plus pitch, yaw, and roll — letting it model angle-of-attack damping and Magnus effects throughout flight. Requires a full aerodynamic coefficient set, not a single BC.

5.2 Drag models, and the trap inside the ballistic coefficient

A standard drag model — a "G-model" — tabulates the drag coefficient of a reference projectile as a function of Mach number. G1 corresponds to a blunt ogival flat-base bullet, the 19th-century Gâvre commission reference; G7 corresponds to a long boat-tail bullet typical of modern match projectiles. Each real bullet is mapped onto its reference by a single scalar, the ballistic coefficient, computed from mass, diameter, and a form factor that is the ratio of the real bullet's drag to the reference's.

The essential caveat is that the form factor is the entire physical content of BC, and it is assumed constant across all velocities. That assumption is the dominant error source in Tier-1 models, and it is why serious solvers support custom drag models — per-projectile Cd-vs-Mach tables — rather than a single BC. Practical implementations also expose G1, G2, G5, G7, and GS tables, and allow the user to import their own. If you must match published ballistic data, plan for custom drag curves from the start; retrofitting them later means rewriting your integrator's force model.

Beware also of hidden normalisation constants. One published implementation notes a Siacci-form deceleration using K = 0.355 calibrated against JBM reference solutions, where the naïve geometric derivation gives π/8 ≈ 0.3927 — the 0.903 ratio folding in the Army Standard Metro reference conditions. Numbers like that are the difference between matching a published table and being quietly 10% wrong at long range. Derive your constants from stated reference atmospheres rather than copying them.

5.3 Atmosphere and environment

For validated output, atmospheric inputs must be independent, not derived from a single altitude figure. Good practice accepts station pressure, temperature, humidity, and altitude as independent inputs, with no silent ICAO defaults at long range. Artillery-grade tools go further, ingesting METCM/METRO meteorological messages or blending from standard-atmosphere presets.

Two second-order effects worth budgeting for because users notice them: a muzzle-velocity temperature coefficient, since powder-temperature-sensitive loads can shift MV by 50–100 fps between summer chronograph data and winter conditions; and rifle cant, where even 2° of cant produces roughly 0.35 mil of unintended windage shift at 10 mils of dial. Coriolis and vertical-plane Eötvös effects enter at long range and are cheap to include once your integrator is in an Earth-fixed frame.

5.4 Implementation recommendations

  • f64 on CPU, always. Non-negotiable given the WGSL/Metal precision ceiling discussed in §2 and §7.
  • RK4 as the baseline, adaptive Dormand–Prince as the upgrade. RK4 with a fixed small step is the common choice and is trivially reproducible. An embedded-error adaptive method buys you accuracy near transonic drag rise, where Cd changes fastest, at the cost of step-size-dependent reproducibility — so make the integrator selectable and record which was used with every result.
  • Decouple the solver from the engine tick entirely. Integrate the trajectory on its own clock — potentially faster than real time, computing the whole flight at trigger-pull — and let the renderer interpolate along the resulting polyline. This is what makes your "interactive but can lag" tolerance a design asset rather than a compromise.
  • Build a regression suite against published data on day one. Store reference trajectories as fixtures; fail the build on drift beyond a stated tolerance. This is the single highest-leverage engineering practice for a project whose requirement is "must match published ballistic data."
  • Treat existing open-source solvers as references, not dependencies. Implementations exist that combine multi-model trajectory engines, atmospheric profile editors, importable drag tables, and DTED/GeoTIFF terrain ingestion — useful for cross-checking your numbers, but a solver you did not write is a solver you cannot defend.

6. Terminal ballistics, penetration, and fragmentation

This is the hardest requirement in your brief, and the place where honesty about what is achievable matters most. FEM/MPM-class penetration with fragmentation cannot run inside an interactive frame budget on consumer hardware. The literature is unambiguous that these are computationally demanding methods, and the research codes that do them well are batch tools, not real-time libraries.

6.1 Why MPM is the right method for this physics

The Material Point Method is a particle method for structural mechanics in which state variables live on Lagrangian material points while a regular structured grid acts as a computational scratch pad for spatial gradients and the conservation equations — and the grid is reset at the end of each time step, so there is no mesh entanglement. An explicit time-stepping MPM formulation has been used specifically to simulate impact, penetration, and fragmentation of metals.

The advantages over FEM for your problem are structural, not incidental: no mesh distortion even under extremely large deformation; exact conservation of mass and linear momentum; a no-slip, no-penetration contact algorithm that comes at no extra cost from the standard formulation; and efficient frictional contact handling thanks to the background grid. It performs well under large deformations and can simulate fracture without re-meshing — precisely the capability FEM lacks, where modelling fracture and splitting is the key challenge. And while MPM can be more computationally expensive than FEM on the CPU, its efficiency can be boosted significantly by GPU acceleration.

Note the historical context: earlier impact, ductile-failure, and fragmentation simulations tended toward Lagrangian approaches with special techniques for fracture and failure. MPM's appeal is that fracture is native rather than special-cased.

6.3 The recommended two-tier architecture

Given the above, the defensible design is to separate ground truth from runtime response.

TIER A
offline
Ground-truth solver. An MPM or FDEM run — OpenFDEM or NairnMPM, or your own Taichi/GeoTaichi implementation — sweeping the parameter space: projectile type, impact velocity, obliquity, target material and thickness. Output: penetration depth, residual velocity, exit-hole geometry, fragment mass distribution and velocity cone. Runs for hours on your Linux workstation, where CUDA is available to you. Results are versioned data, checked into the project.
TIER B
runtime
Surrogate + GPU particles. At impact, interpolate the Tier-A database (or evaluate a fitted analytical/ML surrogate) to get penetration and fragmentation parameters in microseconds. Spawn fragments as GPU-simulated particles in wgpu compute, promoting only significant fragments to Jolt rigid bodies. Deformation shows as a pre-computed damage-state blend, not a live solve.

This architecture gives you three things a monolithic design cannot. It is defensible — every runtime number traces to a continuum-mechanics run you can cite. It is fast — the interactive loop never solves a PDE. And it is incrementally improvable — you refine Tier A without touching the application. It also cleanly resolves your CUDA constraint: CUDA is excluded from the shipped product but perfectly available for the offline tier.

If you later want live continuum response for a hero impact, CRESSim-MPM is the existence proof that GPU MPM with rigid coupling can hit real-time for bounded particle counts — but scope it as a stretch goal on a single showcase target, not the general case.

A gap this review could not close. Validated terminal-ballistics reference data — penetration equations with stated confidence bounds against real test firings — is overwhelmingly in defence-technical literature that is either restricted or not indexed by general web search. The classical open literature (Zukas-era surveys, Curran and Seaman on dynamic failure of metals) is cited in the MPM papers but the underlying test data is not freely available. Plan for this: published external ballistics you can validate against; published terminal ballistics you largely cannot. Your terminal tier will be physically principled and internally consistent rather than empirically validated, and the report recommends you state that limitation in the product itself.

7. Hardware acceleration: what is actually portable

7.1 The precision ceiling

Restating the constraint from §1 because it drives everything else: portable GPU compute across all three of your targets is single precision only. This is a property of the APIs, not of the hardware or of wgpu's design. Mitigations, in order of preference:

  • Keep precision-critical work on the CPU. Trajectory integration is a few thousand steps of a six-state ODE — microseconds in f64 on one core. There is no performance reason to put it on a GPU.
  • Use local-origin coordinates. Store positions relative to a moving reference rather than a world origin. This recovers most of the precision loss for rendering and particle work without needing f64.
  • Compensated summation (Kahan, or a two-float "double-single" representation) in shaders where you genuinely need more than f32 — costly, but well-trodden.
  • Accept f32 for fragmentation. Fragment trajectories over metres do not need f64. This is the natural home for GPU compute in your application.

7.2 CPU acceleration is under-rated here

For your workload, CPU parallelism is likely the better investment. Jolt is built for multi-core from the ground up and will use all cores when objects are spatially distributed. On the solver side, batch trajectory evaluation — Monte Carlo dispersion, firing-solution sweeps, sensitivity analysis — is embarrassingly parallel and maps perfectly onto Rayon in Rust or a simple thread pool in C++, in f64, deterministically, on every platform, with no shader compilation and no driver variance. Explicit SIMD is available and portable: Jolt itself targets a SSE2 baseline with optional SSE4.1/4.2/AVX/AVX2 builds and ARM64 NEON with FP16.

7.3 GPU compute, where it does belong

Three workloads in your application are genuinely GPU-shaped, and all three are served by wgpu compute pipelines: fragment/debris particle simulation (tens to hundreds of thousands of particles, f32, no precision concern); impact-response visualisation — decals, damage accumulation maps, heat and deformation fields written into textures; and volumetric or field rendering if you visualise pressure waves or penetration channels. Add GPU timestamp queries, which wgpu exposes as core API, so you can measure rather than guess.

8. Toolchain and cross-compilation: an honest assessment

You asked for one machine to build all three targets. Here is the real picture.

8.1 Pure Rust: genuinely easy

If every dependency is pure Rust, cross-compilation is two commands: add the target's precompiled standard library, then build against it. The resulting binary is directly runnable on the target; the compiler knows how to lay out the ELF and generate the instructions and does not need a machine of that OS to do it. The catch is precisely stated in the same source: the moment a crate compiles C at build time, the build crashes, because the host's cc targets the host.

8.2 cargo-zigbuild: the pragmatic tool

cargo-zigbuild uses Zig as the linker and C compiler. Zig ships its own C standard library and collates headers and libraries for several architectures, so when it works it is a single command. It covers musl and glibc Linux plus MinGW Windows (x86_64-pc-windows-gnu, with a note that Windows support may be buggier), and it is described as the ideal solution for compiling from macOS to Linux. It uniquely supports pinning a glibc version in the target triple — --target aarch64-unknown-linux-gnu.2.17 — which is the correct way to control Linux binary compatibility. It also supports a universal2-apple-darwin target for macOS universal binaries. Install via cargo, or via pip, which pulls in ziglang automatically.

Its documented caveats are specific enough to plan around: for larger projects using more obscure C features it simply does not work, because Zig's collated headers sometimes rename a symbol the linked binary does not have; -C target-feature=+crt-static for statically linking a glibc version is unsupported; certain RUSTFLAGS such as -C linker silently opt out of using Zig at all; and glibc version checking is imperfect — specifying 2.32 can still produce a binary that runs on a 2.31 host when it should have errored. When Zig fails, the documented fallback is a sysroot, most easily obtained by exporting a Docker image of the target distro to a tarball.

8.3 macOS: the wall

There is no macOS toolchain packaged for Debian or, as far as one practitioner could determine, any Linux distribution. The community answer is osxcross, which extracts and builds a valid toolchain for cross-compiling to macOS from Linux and BSD. But it requires an Apple account and the Apple SDK, used under the terms of the licence Apple provides — and that licence restricts SDK use to Apple-branded hardware. The practitioner account of setting this up describes "a weekend of pain," and the maintainers of the more complete alternative agree it is complex. cargo-zigbuild mitigates this by publishing Docker images with the macOS SDK pre-installed, which is the cleanest available route.

Even with a working cross-toolchain, two things remain impossible off a Mac: code signing and notarisation. A macOS application that is not notarised will be blocked by Gatekeeper on a user's machine. You cannot ship macOS from Linux.

8.4 Recommended build strategy

Daily loop
Develop natively on your primary OS. Use cargo-zigbuild for quick smoke-builds of the other two Linux/Windows targets.
Every commit
GitHub Actions matrix — ubuntu-latest, windows-latest, macos-latest — native compile and test on each. Free for public repos; cheap for private.
Releases
Real macOS runner for signing and notarisation. Non-negotiable.
Discipline
Minimise C dependencies. Every -sys crate is a cross-compilation liability. This is the strongest single argument for Rust-native choices — Rapier or Avian over Jolt-via-FFI, wgpu over a Vulkan C binding.
If C++
CMake with toolchain files per target, plus vcpkg or Conan. Expect to maintain three build environments. A container per target is the sane form of this.

9. Determinism, reproducibility, and tooling

9.1 What determinism costs and where it breaks

Both leading candidates treat determinism seriously — Jolt simulates deterministically enough that replicating inputs replicates the simulation, within documented limits; Rapier was designed from the ground up for determinism and is reported deterministic across platforms. But determinism in a mixed-hardware, multi-threaded, GPU-accelerated application has specific failure modes you should design against:

  • Thread count changes results in most parallel solvers, because reduction order changes. Cross-thread-count determinism is rare enough that a library claiming it treats it as a headline feature. If you need bit-identical replays, either fix the thread count or keep the authoritative simulation single-threaded.
  • Instruction-set variance. Jolt can be compiled for SSE2 through AVX2; different SIMD widths give different floating-point results. Pin one baseline for authoritative runs.
  • Never let GPU results feed back into authoritative state. Shader compilers, driver versions, and fast-math settings vary across vendors and OSes. GPU output is for display; the CPU owns truth.
  • Record provenance with every result: solver version, integrator, step size, drag table identity, atmosphere inputs, thread count, and target triple. This is what makes a result defensible six months later.

9.2 Python bindings

Your Python requirement is well served and should shape the architecture: build the ballistics solver as a library crate first, application second, then expose it via PyO3 and maturin (Rust) or pybind11/nanobind (C++). The payoff is large — parameter sweeps, validation harnesses against published data, plotting, and surrogate fitting for the Tier-A database all belong in Python, calling the same compiled solver the application uses. That guarantees your validation tests and your product share one implementation. Note that ziglang is pip-installable, which means the same Python toolchain can drive your cross-builds.

9.3 Asset pipeline and profiling

On assets: standardise on glTF 2.0 as the interchange format and author in Blender. Bevy's asset system loads from HTTP and HTTPS URLs as of 0.17, which is convenient for a shared reference-geometry library. Godot 4.7 replaced its old Asset Library with a proper Asset Store, though the pool of production-grade paid assets remains smaller than Unity's. For engineering geometry, budget explicit work on CAD-to-render-mesh conversion — it is consistently underestimated.

On profiling, set expectations correctly: deep GPU profiling and debugging tooling for the WebGPU/wgpu ecosystem is years behind Nsight and the CUDA stack. What you do get is workable — Bevy 0.17's frame-time graph widget for at-a-glance history, wgpu's timestamp queries and internal counters for GPU-side measurement, Tracy or perf plus cargo-flamegraph for CPU, and Jolt's own internal profiling framework. Also note Jolt's DebugRendererRecorder, which records physics output to a .jor file for later visualisation — explicitly useful for comparing performance-test output across platforms, though the viewer is Windows-only. A record-and-replay facility of your own, at the solver level, will be worth more than any profiler.

11. Build plan

Phase 0 — Validation harness before anything visual

Rust library crate: f64 point-mass integrator, G1/G7 tables, custom-drag-table loader, independent atmosphere inputs. PyO3 bindings. A test suite comparing against published reference trajectories with a stated tolerance. No graphics. If this phase does not match published data, nothing downstream matters.

Phase 1 — Fidelity ladder

Add modified point-mass, then full 6-DOF with an aerodynamic-coefficient data format. Selectable integrator. Extend the regression suite at each tier — the lower tiers become cross-checks on the higher ones.

Phase 2 — Visualisation shell

Bevy application: terrain, targets, camera, trajectory rendering, a UI for shot parameters. Jolt or Avian for scene rigid bodies. Set up the CI matrix here, before the codebase grows. Simple hit model on impact.

Phase 3 — Terminal ballistics, Tier A

Offline MPM/FDEM studies — OpenFDEM or NairnMPM, or a GeoTaichi-based implementation on your Linux workstation with CUDA. Generate the penetration and fragmentation response database as versioned project data.

Phase 4 — Terminal ballistics, Tier B

Surrogate lookup at runtime, GPU particle fragmentation in wgpu compute, damage-state visualisation, promotion of significant fragments to rigid bodies. Fragment ricochet and secondary impacts if warranted.

Phase 5 — Product surface

Scenario save/load with full provenance, record-and-replay, DOPE-card and report export, Python scripting surface for batch studies, packaging and notarisation.
